## Lens Notes

Startup file-URL routing is correct in the reviewed implementation. `src/electron/main.ts:41` calls `loadFile()` with `{ hash: "/editor" }`, producing a file URL whose fragment is `#/editor`; `src/App.jsx:16-29` selects `HashRouter` only when the document protocol is `file:`. The shared `/editor` route therefore opens the editor instead of interpreting the filesystem pathname as a browser route. For HTTP(S) web use, the same branch continues to select `BrowserRouter`, and the ordinary web build retains root-relative `/assets/` references while the desktop renderer emits `./assets/` references. Some secondary actions still call `window.open()` with absolute web paths such as `/editor`, `/bug-report`, and `/editor/templates/:id`; under a file base these resolve as filesystem URLs instead of hash routes. This is a Medium follow-on gap in new-window routing, not a failure of the repaired initial launch.

Offline/no-server startup is supported by the production path. The focused test executes the built Electron main artifact under a harness, observes one `loadFile()` call targeting `dist-desktop/index.html`, rejects server/network module loading, and verifies the emitted desktop assets resolve to local `file:` URLs rather than localhost. This is strong deterministic integration evidence for the main-process startup contract, although it does not launch Chromium or assert visible editor DOM. The supplied `artifacts/user-smoke/result.json` is successful, but `tests/smoke_manifest.json` and its logs show that it is explicitly the existing Vite web baseline and uses `127.0.0.1:4173`; it must not be cited as Electron/offline launch evidence.

The routing repair introduces no observed security regression: context isolation and sandboxing remain enabled, Node integration remains disabled, and the frozen preload still exposes no generic IPC. The Electron window continues to lack explicit `will-navigate` and `setWindowOpenHandler` policies while the shared renderer contains external links and window-opening calls. That is a Medium hardening gap retained from the scaffold, not a High/Critical routing blocker or a regression caused by choosing `HashRouter` for `file:`.

The repair is focused on the expected surfaces: the Electron load target, the protocol-gated router selection, and the focused runtime test. No unjustified feature or dependency expansion was found. The default `npm test` script still omits the Electron suite, so a normal test invocation can remain green if this routing contract later regresses. Generated `dist`, `dist-desktop`, and `dist-electron` outputs are consistent with the existing separated build design.
